## 1. IDENTITY & AUTHENTICATION ARCHITECTURE

### 1.1 Authentication Boundary
The platform uses **JSON Web Tokens (JWT)** for stateless, verifiable authentication.

* **Token Format**: Signed HMAC-SHA256 (HS256) or RSA-256 (RS256) JWT containing `sub` (User UUID), `tenant_id` (Tenant UUID), `role` (Role Enum), `email`, and `exp` (Timestamp).
* **Storage & Transmission**:
  * For Web Browser Clients: Tokens are transported in **`HTTP-only`**, **`Secure`**, **`SameSite=Strict`** cookies named `access_token`. This eliminates client-side JavaScript access (XSS token theft).
  * For API / Programmatic Clients: Tokens can also be supplied via standard `Authorization: Bearer <token>` headers.
* **Password Security**:
  * Passwords are never stored in plaintext.
  * Hashing algorithm: **Bcrypt** with a work factor cost of 12.

### 1.2 Session Lifecycle
* **Login (`POST /api/v1/auth/login`)**: Validates email/password against the user database, sets the `access_token` cookie with an expiration of 24 hours (or configurable `ACCESS_TOKEN_EXPIRE_MINUTES`), and writes a `USER_LOGIN_SUCCESS` audit event.
* **Current User (`GET /api/v1/auth/me`)**: Returns the authenticated user's profile, role, tenant membership, and assigned permissions.
* **Logout (`POST /api/v1/auth/logout`)**: Clears the authentication cookie and records a `USER_LOGOUT` audit event.

## 2. ROLE-BASED ACCESS CONTROL (RBAC) & PERMISSION MODEL

### 2.1 Role Hierarchy
The platform establishes 5 explicit roles:

1. **`PLATFORM_ADMIN`**: Global system administrator with cross-tenant management, tenant creation, and system configuration capabilities.
2. **`PARTNER_ADMIN`**: DATAEKO / meshIQ engagement manager with administrative privileges across customer engagements within their assigned tenant.
3. **`CONSULTANT`**: Assessment specialist with creation, intake, calculation, audit view, and report generation permissions.
4. **`CUSTOMER_ADMIN`**: Customer enterprise lead with tenant-scoped view, intake completion, report review, and user invitation rights.
5. **`CUSTOMER_USER`**: Customer operational staff with intake completion and read-only executive review permissions.

## 3. MULTI-TENANT ISOLATION & ANTI-IDOR ENFORCEMENT

### 3.1 Tenant Ownership Invariant
Every persistent domain entity is strictly tenant-scoped:
* `User.tenant_id -> Tenant.id`
* `Customer.tenant_id -> Tenant.id`
* `Assessment.tenant_id -> Tenant.id`
* `AssessmentResponse.tenant_id -> Tenant.id`
* `CalculationSnapshot.tenant_id -> Tenant.id`
* `AuditEvent.tenant_id -> Tenant.id`

### 3.2 Anti-IDOR Authorization Flow
Client requests providing a resource ID (e.g. `GET /api/v1/assessments/{assessment_id}`) are subjected to a three-tier validation check:

```text
1. Authentication: Is request authenticated with a valid, non-expired JWT?
2. Tenant Isolation: Does resource.tenant_id match current_user.tenant_id?
3. Role Permission: Does current_user have the required action permission?
```

If a user from **Tenant A** attempts to access or mutate a resource belonging to **Tenant B**, the API returns **`404 Not Found`** or **`403 Forbidden`** with zero metadata leakage (preventing resource enumeration).

## 4. IMMUTABILITY & ENGINE ISOLATION SAFEGUARDS

1. **Snapshot Immutability**:
   * Calculation snapshots generated by the Phase 3 engine are **append-only**.
   * No `PUT`, `PATCH`, or `DELETE` routes exist for snapshots.
   * Modifying responses in an assessment triggers a new calculation execution, which persists a new, distinct, versioned snapshot.
2. **Scenario Sandbox Isolation**:
   * Interactive slider adjustments in the Scenario Sandbox execute in-memory on the client or in transient API models.
   * Changing scenario parameters never modifies the underlying persisted `AssessmentResponse` records or the official `CalculationSnapshot`.

## 5. AUDIT TRAIL ARCHITECTURE

The platform implements an append-only `AuditEvent` entity with the following schema:
* `id`: UUID Primary Key
* `event_type`: Enum (`USER_LOGIN_SUCCESS`, `USER_LOGIN_FAILED`, `USER_LOGOUT`, `CUSTOMER_CREATED`, `ASSESSMENT_CREATED`, `ASSESSMENT_RESPONSES_SAVED`, `CALCULATION_EXECUTED`, `REPORT_GENERATED`)
* `user_id`: UUID of acting user (or null for anonymous failed logins)
* `tenant_id`: UUID of tenant context
* `resource_type`: Target entity name (e.g. `Assessment`, `CalculationSnapshot`)
* `resource_id`: Target entity UUID
* `status`: `SUCCESS` | `FAILURE`
* `ip_address`: Client IP address
* `details_json`: Structured metadata (sanitized of passwords, tokens, or raw financials)
* `created_at`: ISO UTC timestamp

The audit trail is strictly read-only for consultants and administrators, with zero user-facing update or delete capability.

## 6. BROWSER SECURITY & HTTP SECURITY HEADERS

The FastAPI middleware automatically attaches standard defensive HTTP headers to all responses:

* **`Content-Security-Policy`**: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'`
* **`X-Content-Type-Options`**: `nosniff`
* **`X-Frame-Options`**: `DENY` (prevents clickjacking)
* **`Referrer-Policy`**: `strict-origin-when-cross-origin`
* **`Strict-Transport-Security`**: `max-age=31536000; includeSubDomains` (enforced in production)
* **`Permissions-Policy`**: `camera=(), microphone=(), geolocation=()`

## 7. ERROR SANITIZATION & LEAKAGE PREVENTION

* Uncaught server exceptions are intercepted by a global exception handler.
* Internal database connection strings, SQL queries, tracebacks, and local filesystem paths are logged to the server-side console/file but **never returned in HTTP responses**.
* HTTP response bodies return structured error objects:
  ```json
  {
    "detail": "Requested entity not found or access denied",
    "error_type": "EntityNotFound",
    "status_code": 404
  }
  ```

## 8. PRODUCTION DEPLOYMENT & SECRET MANAGEMENT

* All secrets (`SECRET_KEY`, `DATABASE_URL`, `CORS_ORIGINS`) are loaded from environment variables via Pydantic `BaseSettings`.
* Production configuration validates that `SECRET_KEY` is not using the default insecure development string.
* Database connections in production require TLS (`sslmode=require`).
